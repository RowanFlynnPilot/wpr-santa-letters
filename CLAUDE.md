# Letters to Santa — project guide

Wausau Pilot & Review's holiday mailbag, a revival of the feature WPR ran in 2022 and 2024 (one article of letters, first name and age, published Dec. 23, with prizes drawn at random). Built Nov. 7, 2026 on the Buck Board's pattern (`wpr-buck-board`): Supabase + React/Vite on GitHub Pages + a WordPress iframe, Turnstile on the form, staff sign-in by emailed code. There is no voting.

**2026 calendar** (America/Chicago, stored in `seasons`): letters open Nov. 27 (the day after Thanksgiving) · close at the end of Dec. 18 · staff finish the mail, review and run the drawing Dec. 19–22 · delivered Dec. 23 at 6 a.m.: the article runs and winners are public. Shereen can move any of these in `supabase/seasons/2026.sql` before it's run, or with an `update` after.

**How letters arrive** (as in past years): the form (`#/write`, a parent or guardian fills it in for the child), email to editor@, and the mail (Santa, care of WPR, PO Box 117, Wausau, WI 54402; `web/src/contact.ts`). Staff type in emailed and mailed letters at `#/admin` > Add a letter.

**Sponsors:** one presenting sponsor (its logo is the stamp on the mailbag's envelope, or until the logo arrives its name in type, sized so no word ever splits: `widestWord` in `looks.ts`; "Presented by …" under it; Chris's sales plan lists the slot) and any number of supporting sponsors (thanked at the foot). Prizes are their own rows, one per prize to win.

The repo is `wpr-santa-letters`; it must match `base` in `web/vite.config.ts` (`/wpr-santa-letters/`).

**Live in production (as of Nov. 10, 2026):** Supabase project `vhimfuaproejbxahjgpr` (WPR's Pro organization), the app at https://rowanflynnpilot.github.io/wpr-santa-letters/. Every change goes on a branch and through a PR; never push straight to `main`, since a push to `main` deploys (migrations, functions and the web app).

## Invariants — keep these true

1. **The calendar is the state machine.** `phase_at(season, ts)` is the only phase logic: `upcoming` → `open` (the form takes letters) → `closed` (staff finish up and draw) → `delivered`. The web app reads `phase` from `current_season`; nothing is toggled by hand.
2. **Parents send, children don't.** The form is filled in by a parent or legal guardian on the child's behalf, with their consent, which keeps the form clear of COPPA's rules on collecting information directly from children under 13. Never add a field that asks a child for anything, or that publishes more than a first name, age and town.
3. **Public vs. private data.** `letters` holds only what is published: first name, age (0–17; 0 shows as "under 1"), town (optional), the letter, an optional photo. Who sent it, the parent's name and email, a mailed letter's return address, consent, the newsletter opt-in, eligibility and the review trail live in `letter_private` (staff only). No direct writes to either: RPCs only.
4. **One set of rules for the words.** `letter_words()` cleans and checks the first name, age, town and letter for the form (`submit_letter`), staff entry (`add_letter`) and staff edits (`edit_letter`), so the three can't drift. Names and towns are one line (`one_line`), so a last name can't ride along on a second line, and an invisible control character pasted into one is dropped rather than refused. Messages are plain English (`P0001`) and the form shows them as they are; any other error is logged and the parent sees a retry message.
5. **Form letters wait; staff letters don't.** `submit_letter` (service role, from the function only) saves a letter as `pending`; `add_letter` (staff) saves it `approved`, since the staff member typing it is the reviewer. Staff keep the child's spelling and take out last names, street addresses and schools. **A page that's out of date can't undo another editor:** `moderate_letter` takes the status the page showed and `edit_letter` the last edit it saw, and each refuses if the letter has changed since, so a stale tab can't post a letter someone just declined or put back a last name someone took out. **A photo that shows too much, and the photo of any letter that isn't posted or comes down, is deleted:** `remove_letter_photo`, `moderate_letter` (declining or taking down) and `decline_letters` clear `photo_id` and queue it in `photo_deletions`, in the same transaction; the staff browser then deletes both files and the queue row. If that answer never reaches the browser (the tab closed, the network dropped), the next time Review letters opens it finishes the queue; if a delete fails, the staff page says so with the folder to delete by hand. Photos are cached for an hour, not a year: on Supabase Pro the Smart CDN drops a deleted photo within about a minute, but a browser that already loaded it keeps its copy for as long as the cache header says. **Junk is declined in bulk:** on Waiting for review, Find narrows the list, Select all shown (or a letter's own Select) picks them, and `decline_letters` declines them all with one reason, refusing if any has changed since the page loaded.
6. **Explicit privileges only.** Migration 0003 revokes everything from `anon`, `authenticated` and `service_role` and grants exactly what's needed; readers see a winner's draw but not who ran it. Postgres still lets PUBLIC execute any new function until it's revoked, which no per-schema default can change, so a migration that adds a function revokes it from public itself (as 0005 does). `04_privileges.test.sql` lists every table privilege and function each API role has, so anything new that grants access, on purpose or not, fails CI until the list is updated. The suite passes with and without Supabase's permissive default grants.
7. **Security definer functions** set `search_path = ''` and fully qualify names. **Views** are `security_invoker`. `04_privileges` checks both, and that every table has RLS on.
8. **Photos:** the browser decodes once as an `<img>`, which applies the photo's orientation in every browser in use (Safari since 13.1; `createImageBitmap`'s option for it needs Safari 17), lays it on white (a transparent PNG drawing stays readable), and encodes a 1600px full image and a 640px thumbnail. `submit-letter` strips APP1/APP13 (Exif/XMP/IPTC, GPS included) from both, stores them as `letter-photos/<photo_id>/full.jpg` and `/thumb.jpg` with an hour's cache header (invariant 5), then calls `submit_letter()`; if the letter isn't saved, it removes both. Staff uploads (a scan of a mailed letter) go through the same browser encoding, which writes no metadata; `add_letter` refuses a photo whose two files aren't both uploaded. The only `storage.objects` policies let staff insert, see and delete in `letter-photos`. **In the mailbag the photo leads its letter** (`LetterCard`): the child's own hand first, the typed words under it. The wall loads the 640px thumbnail, in a frame no taller than 4:5 that's held open before the photo arrives; a taller page shows its top, with a button that opens all of it from the full-size file. Only the one letter a reader followed a link to loads the full-size file up front.
9. **Bots stop at the door.** `submit-letter` verifies the Turnstile token with Cloudflare before it stores anything. One email address can send at most 10 letters in a rolling day, its +tags counted together, under the season's lock so parallel sends can't slip past. **A retry never makes a second letter:** the form gives each letter a key (`submission_key`, kept across retries, new for the next letter); if a try saved the letter but its reply was lost, the retry gets that letter back from `submit_letter` (`repeat: true`), the function deletes the retry's copy of the photo, and the emails go again with the first try's idempotency keys, which Resend drops.
10. **The drawing is fair.** `run_prize_drawing` runs after letters close, only when no letter is waiting for review, and draws each prize once; run again, it draws only prizes added since (a late sponsor) and never touches a winner. Every letter in the mailbag is a ticket, except staff households' and letters with no way to reach the family; one prize per family. A staff household is a family: `set_prize_eligible` changes every letter of the family, and a letter that arrives later takes the family's mark (`keep_household`). `family_key` is the email without any +tag, or the return address reduced to lowercase letters and digits ("12 Elm St., Wausau" = "12 elm st wausau"); a mailed letter and a form letter from one family only match if staff enter the parent's email on the mailed one. `redraw_prize(draw_id)` forfeits that exact draw (a page that's out of date can't forfeit a newer winner) and draws again among families holding nothing. A current winner can't be taken down or its family marked a staff household. Once the drawing has run, no ticket is added: no new letter, no declined letter posted, no household put back. **The season lock** (`lock_season`, an advisory lock taken first by the drawing, a redraw, a moderation, an eligibility change, a new staff letter and a new form letter) keeps two editors from interleaving: two redraws at once can't hand one family two prizes. Winners are public from `delivered_at`, current winners only. "One family" is matched by address, not by name: two parents' different emails, or a mailed letter typed in without the parent's email, count as two families, so glance down the winners for a shared last name or street before contacting them (decided Nov. 7: that check is enough). Sponsors' households can enter and win; only staff households can't.
11. **Fail fast.** Missing env vars stop the function at load (`SUPABASE_SECRET_KEYS` needs a `default` key) and the web build at build time. Email is the one optional setting: without `RESEND_API_KEY`, letters save and nothing is sent. Anyone can type any address into the form, so the parent's confirmation carries nothing typed into it (no names, no town, no words): the form can't be used to send someone's chosen text from santa@ to a stranger. The editor's morning digest (invariant 20) carries a short excerpt of each waiting letter, to staff only; the posted email, which goes only after an editor has read the letter, names the child. The function logs a database error's code and message only, never its details, which repeat the family's words.
12. **The mailbag and the form never load the Supabase client.** Inside WordPress the app is a third-party frame, and a browser that blocks third-party cookies (Chrome Incognito, by default) refuses storage there; the client opens storage as it loads, which took the form down until Nov. 7. `reads.ts` and `send.ts` use plain fetch with the publishable key, in the `apikey` header only (it isn't a JWT; `Authorization` carries a signed-in staff member's token or nothing). Only `#/admin`, opened directly, loads the client. The front-page strip (`#/embed`) and Santa's reply (`#/reply`) follow the same rule.
13. **The posted email goes once, and only for a posted letter.** When staff post a letter that has an email (Post it, or Add a letter with an email), the staff browser calls `letter-posted`, which checks the caller is staff, sends the parent a note with a link to the letter and one to Santa's reply (invariant 22), then stamps `posted_notice_at`. `posted_notice()` answers only for an approved letter with an email and no stamp, and Resend's idempotency key (`santa-letters-<id>-posted`) drops a repeat, so a double click or a retry can't send twice. A failed send (Resend's daily limit, shared with the Buck Board, is the likely cause, or the function unreachable) never undoes the post: the letter stays up, the staff page names every family whose email didn't go, and the letter itself says "The family hasn't been emailed that it's up" under In the mailbag, with Email the family the link to send it again. The same note shows when nothing was sent at all (email off), since the stamp, not the click, is the record. It names the child and never carries the letter; whether it mentions the drawing and invites more letters comes from `posted_notice()` (the family isn't a staff household; `phase_at` says open), so the email has no phase logic of its own.
14. **A link to one letter is `/letters-to-santa/#letter=<id>&from=<where>`**, from the posted email (`email`), Share (`share`), the strip (`front-page`) and the newsletter (`newsletter`). `embed.js` turns it into a fresh frame at `?letter=<id>&from=…#/mailbag`, a new iframe rather than a new `src`, because Chrome can let a frame's first load win over a `src` changed while it's under way. `linked.ts` reads it once, first, and takes it off the address before analytics loads: Plausible records where the reader came from (`Letter Opened`, `from`) and never which letter. The mailbag shows that letter first and scrolls to it. Santa's reply is the one link straight to the app, `?letter=<id>&from=<email|staff>#/reply`, read the same way (`Santa Reply Opened`, `Santa Reply Printed`).
15. **The privacy check advises; it never blocks.** `privacyFlags()` looks for a street address, phone number (10 digits run together too), email, web address, school, teacher's name ("mrs smith" too), a first name followed by a capitalized or all-capitals word (a last name), and a second word in the name box. The form asks the parent to take out what it finds; Review shows staff the same note on a waiting letter. A letter sends and posts either way: the editor decides. The newsletter picker shows the note too and never ticks a flagged letter for staff: it goes to every subscriber only if someone ticks it.
16. **No sideways scroll**, at 320px or at 200% text. `body` wraps a word longer than its space anywhere (`overflow-wrap: anywhere`, which, unlike `break-word`, lets grids and flex rows shrink past a long email address), and every auto-fit grid is `minmax(min(100%, X), 1fr)`. The strip shows as many of the newest four letters as fit whole (container queries, 13rem each), never a sideways row; at very large text it scrolls inside its frame rather than cutting off its buttons.
17. **Staff work survives a look elsewhere.** A staff tool unmounts when another tab is picked, so a half-typed letter and the article's edited intro and closing live in `useDraft` for the life of the page. After an action that leaves a letter in its list (removing a photo, an edit, a household mark, a redraw), its buttons come back. Add a letter says so once the drawing has run instead of offering a form the database would refuse.
18. **What staff paste stays inert.** The article and the newsletter block escape every word, and put an invisible word joiner after each `[`, so a letter can't carry a WordPress shortcode ("[gallery …]") or a newsletter merge tag ("[[…]]") through the visual editor, which turns `&#91;` back into `[` when it parses a paste.
19. **Families' details last two weeks past delivery.** `forget_families()` clears every family's name, email, return address and newsletter opt-in once a season is 14 days past `delivered_at` (Jan. 6 for 2026), stamping `forgotten_at`; the letters, published or not, stay. A daily pg_cron job runs it at 12:05 UTC (6:05 a.m. in Wausau), so it happens whether or not anyone remembers, and no API role can call it. Winners get 7 days to reply (`REPLY_DAYS` in Prizes.tsx, and the rules), which leaves a round of redraws before the details go. Pro's daily backups (7 days) still hold them until about Jan. 13. The staff pages say a family's details were cleared rather than showing blanks.
20. **The editor hears about waiting letters once a morning.** No email per letter: at 13:00 UTC (7 a.m. in Wausau all season) a pg_cron job (migration 0008) has `pg_net` call `staff-digest` with the project's secret key, both read from Vault (README, First deploy). The key goes in the `apikey` header: a secret key isn't a JWT, and Supabase's gateway rejects one sent as a bearer token. The call waits up to 30 seconds (pg_net's default is 5, short for a cold start plus Resend). The function accepts only that key, lists the active season's waiting letters, oldest first (first name, age, town, when, whether there's a photo, the first 140 characters; the first 25, then a count of the rest), and emails `STAFF_EMAILS` with a link to Review; when nothing waits, it sends nothing. Its Resend key is the date (`santa-letters-digest-<date>`), so a repeat call that day sends nothing more. It needs no browser origin: it's called by the database, never a page.
21. **The newsletter section is saved, not pasted.** Staff save the Letters to Santa section for a morning (`save_newsletter_section`: one to three posted letters, a morning in the season, before 6:45 a.m. that day since the edition is built at 6:58, at most 13,000 characters); `newsletter_sections` holds it by season and date. Readers (the publishable key) see a section only from its own morning in Wausau and only while every letter in it is still up, so wpr-newsletter's build, which reads it at about 7 a.m., never carries a letter that came down. A saved section is a copy of its letters' words, so editing one of them withdraws every section holding it that hasn't gone out (a trigger); the edit form says so, and staff save that morning again. Without a saved section, the build leaves it out.
22. **Santa's reply promises nothing.** `#/reply` reads one letter from the public `mailbag` view (`loadLetter`), so it exists only while the letter is up, and speaks to the child by first name and town (and thanks the grown-up for children 4 and under). It never mentions gifts or what the child asked for: no family is promised anything by a newsroom page. The postmark carries the day it's printed. It prints on one letter-size sheet (print styles hide the button and the page background). The presenting sponsor's stamp sits in the corner, `santa-reply` placement.
23. **Applied migrations are history, never edited.** Migrations 0001–0008 (`20261107000001` through `20261107000008`) are applied in production, so `supabase db push` will never run them again: an edit to one changes nothing live and leaves the repo describing a database that doesn't exist. Every schema change, however small (a grant, a comment, a fixed function body), goes in a new migration file with a later timestamp (`supabase migration new <name>`), which redefines what it changes (`create or replace function`, `alter table`, `revoke`/`grant`) and revokes any new function from public (invariant 6). A comment in an applied migration that has gone stale (0008's Vault SQL) is corrected in the README or here, not in the migration. The same goes for `supabase/seasons/2026.sql`, already run: change the season with an `update` (Operations).

## Operations (SQL editor)

From a Windows `psql`, set `PGCLIENTENCODING=UTF8` first, or curly apostrophes in sponsor names garble.

```sql
-- Staff: each user must exist first (Dashboard > Authentication > Add user). Shereen signs in with editor@.
insert into public.staff (user_id) select id from auth.users
where email in ('editor@wausaupilotandreview.com', 'rowan.flynn@wausaupilotandreview.com');

-- The presenting sponsor: logo_path is the logo's object name in the sponsor-logos bucket, uploaded first;
-- leave it out until the logo arrives, and the stamp sets the name in type. Names up to 80 characters.
insert into public.sponsors (season_id, name, tier, logo_path, website_url)
select id, 'Example Bank', 'presenting', 'example-bank.png', 'https://example.com' from public.seasons where year = 2026;

-- A supporting sponsor.
insert into public.sponsors (season_id, name, tier, website_url)
select id, 'Example Pizza', 'supporting', 'https://example.com' from public.seasons where year = 2026;

-- Prizes: one row per prize to win, written to follow "wins" (lowercase "a"; the database refuses "A …",
-- "An …" and "The …"), up to 120 characters.
-- A sponsor giving three gift cards gets three rows; the mailbag lists them once, "(three to win)".
-- The drawing gives them out in the order they were added.
insert into public.prizes (season_id, sponsor_id, description)
select s.id, sp.id, 'a family pizza night'
from public.seasons s join public.sponsors sp on sp.season_id = s.id and sp.name = 'Example Pizza'
where s.year = 2026;

-- A logo that arrives later.
update public.sponsors set logo_path = 'example-pizza.png' where name = 'Example Pizza';

-- Newsletter opt-ins from the form, for import: posted letters only, so a junk letter's address never lands on the list.
-- Export them before Jan. 6: the clearing (invariant 19) takes the addresses with everything else.
select distinct p.email from public.letter_private p join public.letters l on l.id = p.letter_id
where p.newsletter_opt_in and l.status = 'approved' order by p.email;

-- The two daily jobs (clearing families' details, the morning digest), and how their runs went. A digest
-- run "succeeded" once pg_net queued the call; the call's own answer is in net._http_response.
select jobname, schedule, command from cron.job;
select j.jobname, d.status, d.return_message, d.start_time
from cron.job_run_details d join cron.job j using (jobid) order by d.start_time desc limit 10;
select status_code, content, created from net._http_response order by created desc limit 5;

-- Send this morning's digest now (it sends once a day; a second call that day is dropped by Resend).
-- Paste the command from cron.job where jobname = 'santa-letters-staff-digest'.

-- Replacing a Vault secret (a rotated secret key, a new project URL): not here. Use the dashboard's Vault
-- screen (Integrations > Vault > Secrets) and edit `santa_secret_key` or `santa_project_url` in place,
-- keeping the name. Production's were set there, not with vault.create_secret from the SQL editor.
-- Check the digest's job still reads them (both rows, no values shown):
select name, updated_at from vault.secrets where name in ('santa_project_url', 'santa_secret_key');

-- Moving a date (here, opening a week earlier).
update public.seasons set entries_open_at = timestamptz '2026-11-20 00:00 America/Chicago' where year = 2026;

-- Photos left in storage with no letter (a form upload that failed partway, or a queued deletion no one
-- has opened Review to finish): their folders, to delete in Storage > letter-photos. A form letter's
-- folder exists a moment before its letter does, so ignore any from the last few minutes.
select split_part(name, '/', 1) as folder, min(created_at) as uploaded
from storage.objects
```
